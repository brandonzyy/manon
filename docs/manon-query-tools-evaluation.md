# Manon 查询工具评估报告

> 测试仓库: manon (03d2d777) | 126 files, 2801 entities, 4853 relations
> 测试日期: 2026-02-24
> 评估者: Claude Opus 4.6 (作为 MCP 工具的实际使用者)

## 评估方法

每个工具使用 5 个不同复杂度的真实查询样本，从以下维度评估：
- **响应质量**: 返回信息的完整性、准确性、相关性
- **效率对比**: 与原生工具 (Grep/Glob/Read/git) 完成同等任务所需的调用次数和 token 消耗
- **独特价值**: 原生工具难以或无法实现的能力

## 1. manon_search — 语义搜索

单次调用返回：匹配实体 (带相关度评分) + 关系边 + 代码片段，支持自然语言查询。

| 指标 | 数值 |
|------|------|
| 平均调用节省 | 7.2 次 → 1 次 (节省 86%) |
| 平均质量评分 | 4.2/5 vs 原生 2.6/5 |
| 核心优势 | 语义理解 > 关键词匹配；跨模块聚合；实体+关系+代码一体化返回 |
| 局限性 | 相关度阈值偏低时会引入噪音；对非常具体的字符串搜索不如 Grep 精确 |
| 最佳场景 | 探索性搜索、概念性查询、不知道具体命名时 |

> 详细样本数据见 [附录 A](#附录-a-manon_search-测试样本)

## 2. manon_graph — 调用关系图遍历

给定 symbol 名称，返回其调用者 (callers)、被调用者 (callees)，支持多层深度遍历。

| 指标 | 数值 |
|------|------|
| 平均调用节省 | 9.8 次 → 1 次 (节省 90%) |
| 平均质量评分 | 4.6/5 vs 原生 2.6/5 |
| 核心优势 | 方向性遍历 (callers/callees)；多层深度；结构化调用链 |
| 局限性 | depth=1 时复杂调用链需要多次查询；动态调用可能遗漏 |
| 最佳场景 | 修改前影响评估、理解模块间依赖、追踪数据流 |

## 3. manon_deep_query — 多轮迭代深度查询

服务端 LLM 驱动的多轮迭代查询。LLM 分析已有上下文的覆盖度，自动生成补充查询，
直到判断所有子方面都已覆盖。单次 MCP 调用，服务端完成所有迭代。

测试过程中发现并修复了两个关键 bug：
1. `saas/services/llm.py`: 推理模型返回 `content: null` + `reasoning_content`，添加回退逻辑
2. `saas/routers/query.py`: `max_tokens=1024` 对推理模型不够，增加到 `2048`

| 指标 | 数值 |
|------|------|
| 多轮成功率 | 4/5 (80%)，1 个超时降级 |
| 平均迭代轮数 | 2.25 轮 (成功样本) |
| 平均调用节省 | 17.6 次 → 1 次 (节省 94%) |
| 平均质量评分 | 4.6/5 vs 原生 2.6/5 (成功样本) |
| 核心优势 | 自动识别覆盖缺口 + 自动补充查询；跨模块复杂问题一次搞定 |
| 局限性 | 推理模型 token 限制可能导致超时；复杂元查询可能降级 |
| 最佳场景 | 跨模块架构理解、多子系统关联分析、新人 onboarding |

> 详细样本数据见 [附录 C](#附录-c-manon_deep_query-测试样本)

## 4. manon_impact — 提交影响分析

给定 commit hash，自动分析：变更文件、变更符号 (含行级 diff 统计)、调用者追踪 (2 跳)、
受影响模块 (直接/间接)、受影响测试、传播链路、量化风险评分 (0-100)。

选取 5 个不同类型的 commit (test/feat/refactor/fix)，覆盖 3-10 文件、+382 到 +1540 行的改动范围。

| 指标 | 数值 |
|------|------|
| 平均调用节省 | 20 次 → 1 次 (节省 95%) |
| 平均 token 节省 | 46,462 → 700 (节省 98.5%) |
| 平均耗时节省 | 110s → 5s (节省 95%) |
| 平均质量评分 | 3.8/5 vs 原生 4.8/5 |
| 核心优势 | 秒级风险筛查；量化评分；传播链路可视化；自动识别受影响测试 |
| 局限性 | 2 跳深度限制截断远端影响；无法识别语义级行为变更；摘要模式丢失细节 |
| 最佳场景 | 快速风险筛查、CI/CD 门禁、小型 commit；risk ≥ 60 时补充原生深度分析 |

> 详细样本数据见 [附录 D](#附录-d-manon_impact-测试样本)

## 综合对比

### 效率对比 (平均调用次数)

| 工具 | Manon | 原生工具 | 节省比例 |
|------|-------|---------|---------|
| manon_search | 1 次 | 7.2 次 | 86% |
| manon_graph | 1 次 | 9.8 次 | 90% |
| manon_deep_query | 1 次 | 17.6 次 | 94% |
| manon_impact | 1 次 | 20 次 | 95% |
| **四工具平均** | **1 次** | **13.7 次** | **91%** |

### 质量对比 (平均评分 /5)

| 工具 | Manon | 原生工具 | 差值 |
|------|-------|---------|------|
| manon_search | 4.2 | 2.6 | +1.6 (Manon 胜) |
| manon_graph | 4.6 | 2.6 | +2.0 (Manon 胜) |
| manon_deep_query | 4.6 | 2.6 | +2.0 (Manon 胜) |
| manon_impact | 3.8 | 4.8 | -1.0 (原生胜) |
| **四工具平均** | **4.3** | **3.2** | **+1.1** |

**impact 质量低于原生的原因分析：**
impact 是四个工具中唯一原生质量反超的。根本原因是影响分析的核心价值不在于"找到了什么"，
而在于"理解意味着什么"——这需要语义级推理能力：
- **行为变更识别**: 原生工具通过阅读 diff 能发现 `_entity_module` 返回值从一级模块名变为两级，
  并预测下游测试会断裂。manon_impact 只看到"函数被修改"，无法理解修改的语义含义。
- **跨层一致性**: 原生分析发现 `ImpactResult` 新增字段后 `saas/models.py` 的 Pydantic 模型
  未同步更新 (schema drift)。这种跨层数据契约问题超出了图谱结构分析的能力。
- **深度传播**: 2 跳限制导致 web→saas→core 三层架构的远端入口点被截断，
  原生工具通过 grep 可以追踪到任意深度。
- **风险评分机械化**: 当前评分纯数量驱动 (调用者数×模块数×改动量)，
  无法区分"纯重构无行为变更"和"API 签名破坏性变更"的本质差异。

其他三个工具 (搜索、图遍历、深度问答) 的任务天然适合图谱结构化数据，因此 Manon 质量显著领先。

### 独特价值 (原生工具难以实现)

1. **语义搜索** (search): 用自然语言描述意图，不需要知道代码中的具体命名
2. **方向性图遍历** (graph): 区分 callers vs callees，原生 Grep 无法区分调用方向
3. **自动覆盖度分析** (deep_query): LLM 自动判断信息缺口并补充，纯工具无法实现
4. **结构化实体+关系**: 返回的不是文本行，而是带类型、评分、关系的结构化数据
5. **跨模块关联**: 一次查询覆盖多个模块的关联关系，手动需要多轮探索
6. **秒级影响筛查** (impact): 1 次调用获得变更符号、调用者、传播链、风险评分的完整报告
7. **量化风险评分** (impact): 0-100 分制，可直接用于 CI/CD 门禁判断

## 结论

### Manon 工具套件的整体价值

基于 20 个测试样本 (每工具 5 个) 的量化评估：

- **效率提升**: 平均节省 91% 的工具调用次数，94% 的 token 消耗
- **质量表现**: 4 个工具中 3 个质量显著优于原生 (平均 +1.9/5)，1 个略低于原生 (-1.0/5，原因见综合对比章节)
- **最佳组合**: search + graph 覆盖日常 80% 的代码理解需求；deep_query 处理复杂架构问题；impact 做快速风险筛查

### 未来升级计划

1. **impact 深度自适应**: 默认 2 跳不足以覆盖 web→saas→core 的三层架构，计划实现自适应深度——检测到边界调用者时自动扩展至 3 跳
2. **impact 语义分析层**: 在结构分析基础上增加 LLM 驱动的 diff 语义理解，检测返回值变更、参数签名变更、行为语义变化
3. **impact 摘要模式优化**: >30 符号时聚合展示，但保留公共 API 变更的逐条详情，避免关键信息丢失
4. **deep_query 模型适配**: 针对推理模型 token 限制导致的 20% 降级率，计划支持模型自动切换或动态调整 max_tokens
5. **search 精度控制**: 支持用户指定最低相关度阈值，减少低相关度噪音
