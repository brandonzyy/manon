# Manon — AI 架构师，为你的代码而生

---

## 一、AI 编程的结构性困境

AI 编程正在改变软件开发，但当前的 AI 编程工具存在两个根本性缺陷，使得 AI 无法真正可靠地完成复杂开发任务。

### 缺陷一：上下文不足

AI 模型在编写代码时，无法看到完整的调用图、依赖链和模块边界。它只能基于当前打开的文件和有限的上下文进行推理，导致：

- **幻觉** — 猜测函数之间的调用关系，猜错就引入 bug
- **遗漏** — 修改一个函数却不知道有 20 个调用方会受影响
- **重复** — 不知道项目中已有类似功能，重新实现一遍

这个问题在三个层面都会造成失败：

| 层面 | 失败模式 | 具体表现 |
|------|---------|---------|
| **架构层** | 看不到全局做结构决策 | 不必要的抽象层、过度模块化、过早泛化、配置/事件系统过度设计 |
| **模块层** | 不理解依赖关系就划分边界 | 单模块功能膨胀、职责不清、跨模块重复、过度耦合 |
| **代码层** | 不知道谁调用谁就修改代码 | 死代码残留、引入循环依赖、函数拆分过细、内聚性低 |

### 缺陷二：流程缺失

AI 模型倾向于跳过需求分析、测试和验证，直接编写代码。没有结构化的开发流程，导致：

- **范围蠕变** — 需求不明确就开始写代码，越写越偏
- **未测试的代码** — 写完功能不补测试，上线后出 bug
- **静默回归** — 修改代码后没有验证，破坏了已有功能

### 为什么模型越强，问题越严重？

- **AI 无法"感知"架构意图** — 它局部优化，产出技术上正确但违反系统设计的代码
- **AI 生成速度远超验证速度** — 没有图谱验证，错误模式以机器速度扩散
- **每次 AI 会话都是从零开始** — 没有对过去决策的记忆，同样的结构错误反复出现

**强模型 + 差上下文 + 无流程 = 自信的垃圾，速度更快。**

## 二、Manon 的解决方案

Manon 从根源解决这两个问题：通过**知识图谱**补全上下文，通过**开发技能**规范流程。

### 设计哲学

Manon 的核心设计原则是 **"让 AI 基于代码事实做决策，而非基于想象"**。每一个功能都围绕这个原则构建：

1. **数据留在本地** — AST 解析、图谱、向量、代码块全部落在项目的 `.manon/` 目录，源代码不离开开发者机器；无服务端、无数据库、无后台进程
2. **增量同步** — 文件 SHA-256 哈希判定变更，只重建改动文件
3. **混合检索** — 图遍历（结构性）+ 向量搜索（语义性），精准获取相关代码
4. **技能只做 AI 做不好的事** — 如果纯对话能完成，就不需要技能

### 系统架构

**纯本地（manon-kg CLI，单进程按需运行）**

| 组件 | 职责 |
|------|------|
| manon-kg CLI | 唯一入口：sync / query / graph / deep-query / impact / health / status |
| core/ast + codeindex/ | tree-sitter AST 解析与各语言专用解析器 |
| 图谱存储 | NetworkX 有向图，落 `<项目>/.manon/graph/` |
| VectorIndex | numpy 余弦相似度检索，向量与代码块同落本地 |
| deep-query | 本地 CLI 编排的 LLM 多轮规划 |
| embedding 客户端 | 调用向量嵌入 API（BAAI/bge-m3） |
| skills | /manon（图谱使用规则）+ /assurance（工程保障体系） |

**数据流向**：本地扫描文件 → AST 解析 → 图谱 + 向量落 `<项目>/.manon/` → 查询在本地完成并返回

## 三、知识图谱 — 核心基础

知识图谱是 Manon 的核心基础。它索引代码库中的每一个函数、类、方法、调用关系、导入链和模块边界，构建一个完整的代码结构图。

### 索引内容

Manon 通过 tree-sitter 进行 AST 级别的代码解析，提取以下结构信息：

| 提取项 | 内容 |
|--------|------|
| **实体 (Entities)** | 函数、类、方法、模块、变量 |
| **关系 (Relations)** | 调用 (calls)、导入 (imports)、继承 (inherits)、处理 (handles) |
| **代码块 (Chunks)** | 每个实体的代码片段，用于向量检索 |
| **HTTP 路由** | Flask/FastAPI、Express、NestJS 的路由注册（HANDLES 边类型） |

### 混合检索机制

Manon 的检索不是简单的关键字搜索，而是**向量搜索 + 图遍历**的混合模式：

1. **向量搜索**：将查询转为向量嵌入，与代码块向量计算余弦相似度，找到语义最相关的实体
2. **图扩展**：沿图谱边展开，自动关联调用方、被调用方、同模块实体
3. **结果融合**：返回实体 + 关系 + 代码片段的结构化结果

这使得 Manon 能够回答"描述性"的问题（不知道关键字，用自然语言描述意图），而传统的 Grep 只能搜索已知关键字。

### 语言支持

**深度解析**（符号 + 调用 + 导入 + 继承 + 路由提取）：

Python, TypeScript, JavaScript, Java, PHP

**通用解析**（符号 + 导入，基于 tree-sitter 自动下载）：

Go, Rust, C, C++, C#, Ruby, Swift, Kotlin, Scala, Lua, R, Elixir, Dart, Haskell, OCaml, Bash, Zig

## 四、四大查询工具

Manon 提供四个查询能力（manon-kg 子命令），覆盖从代码搜索到风险评估的完整场景。

### 4.1 `manon-kg query` — 语义代码搜索

**解决的问题**：不知道关键字时，如何找到相关代码？

**工作原理**：自然语言 → 向量嵌入 → 检索最相似实体 → 沿图谱边扩展关联代码

**典型场景**：
- "处理用户认证的函数在哪里？"
- "数据库连接池是怎么管理的？"
- "WebSocket 消息路由逻辑"

**对比原生工具的优势**：

| 维度 | manon-kg query | Grep |
|------|-------------|------|
| 查询方式 | 自然语言描述意图 | 必须知道精确关键字 |
| 返回内容 | 实体 + 关系 + 代码片段 | 匹配的文本行 |
| 跨模块关联 | 自动关联调用方/被调用方 | 每个文件独立，需手动跳转 |
| 工具调用次数 | 1 次 | 平均 7.2 次 |
| 质量评分 | 4.2/5 | 2.6/5 |

### 4.2 `manon-kg graph` — 调用图遍历

**解决的问题**：修改一个函数前，如何知道谁在调用它？改了之后会影响什么？

**工作原理**：给定符号名 → 在图谱中定位 → 按方向遍历调用边 → 返回多层调用链

**参数**：
- `symbol`：函数/类名
- `--direction`：`callers`（谁调用我）/ `callees`（我调用谁）/ `both`（双向）
- `--depth`：遍历深度（1-3 层）

**关键能力**：Grep 无法区分"调用方"和"被调用方"——搜索一个函数名会返回所有出现位置，无法判断方向。manon-kg graph 提供**有方向的**调用关系。

**实测对比**：

| 维度 | manon-kg graph | 原生工具 |
|------|------------|---------|
| 工具调用次数 | 1 次 | 平均 9.8 次 |
| 质量评分 | 4.6/5 | 2.6/5 |
| 核心优势 | 有方向的调用链、多层深度 | 无法区分调用方向 |

### 4.3 `manon-kg deep-query` — 多轮深度查询

**解决的问题**：跨模块的架构问题，需要多次查询才能拼出完整图景。

**工作原理**：
1. 用户提出架构级问题
2. CLI 编排的 LLM 分析已有上下文，识别信息缺口
3. 自动生成补充查询，在图谱中搜索
4. 重复直到所有子问题都被覆盖

**典型场景**：
- "项目的认证流程是怎样的？从前端到数据库经过哪些模块？"
- "这个项目的多通道集成是如何设计的？各通道之间有什么依赖？"

**关键价值**：一次 CLI 调用自动完成所有迭代，不需要人工一轮轮提问。

**实测对比**：

| 维度 | manon-kg deep-query | 原生工具 |
|------|-----------------|---------|
| 工具调用次数 | 1 次 | 平均 17.6 次 |
| Token 消耗 | ~8K | ~73K |
| 质量评分 | 4.6/5 | 2.6/5 |
| 平均迭代轮数 | 2.25 轮（自动完成） | 需人工多轮查询 |

### 4.4 `manon-kg impact` — 提交影响分析

**解决的问题**：提交代码前，如何快速评估这个提交的风险？

**工作原理**：解析 git diff → 提取变更符号 → 在图谱中追溯 2 跳调用方 → 计算风险分（0-100）

**返回内容**：
- 变更的符号列表（函数、类）
- 直接调用方
- 间接调用方（2 跳）
- 受影响的模块
- 受影响的测试
- 传播链可视化
- 量化风险评分

**应用场景**：
- CI/CD 流水线中作为质量门禁
- 代码审查的辅助工具

**实测对比**：

| 维度 | manon-kg impact | 原生工具 |
|------|-------------|---------|
| 工具调用次数 | 1 次 | 平均 20 次 |
| Token 消耗 | ~3.5K | ~232K（节省 98.5%） |
| 耗时 | ~5 秒 | ~110 秒 |

### 四工具综合效能

| 指标 | Manon | 原生工具 | 提升 |
|------|-------|---------|------|
| **平均工具调用** | 1 次 | 13.7 次 | **减少 91%** |
| **总 Token 消耗** | ~19.5K | ~350K | **节省 94%** |
| **平均质量评分** | 4.3/5 | 3.2/5 | **+34%** |

## 五、两个开发技能

Manon 的技能系统由两个技能组成：/manon 负责图谱使用规则，/assurance 是工程保障体系的唯一入口。每个循环都以知识图谱或确定性脚本为支撑，确保决策基于代码事实。

技能只在 AI 纯对话无法完成时才存在——它们要么需要外部工具集成（本地图谱 CLI、覆盖率数据），要么需要确定性工作流，要么需要结构化输出。

| 顺序 | 阶段 | 技能 | 输入 | 输出 |
|------|------|------|------|------|
| 1 | 激活图谱 | /manon | 项目代码 | 索引 + 图谱使用规则 |
| 2 | 编码开发 | AI + 图谱 | 需求 | 功能代码 |
| 3 | 工程保障 | /assurance | 项目读数 | 分诊到五条循环之一 |

### 5.1 /manon — 图谱使用规则

**做什么**：给出 manon-kg 六个子命令的适用边界——什么场景用 query、什么场景用 graph、
什么时候必须 sync。

**为什么需要技能**：索引状态与健康度的完整呈现、六个子命令的选择判据是确定性规则，
不该靠对话临场发挥。

### 5.2 开发阶段 — AI + 图谱

**做什么**：AI 正常写码，图谱维护与查询是显式纪律，由 /manon 技能规则约束执行。

**工作规则**：
- **每次任务后**：`manon-kg sync` 把结构变化并入图谱（增量，只重建改动文件）
- **定位代码先 query**：拿到 `路径:行号` 再截读，不通读整文件
- **改公共函数/跨模块前**：`manon-kg graph 符号 --direction callers` 看调用方，
  `manon-kg impact --commit HEAD` 看影响传播

### 5.3 /assurance — 工程保障体系

**做什么**：回答「这个项目到底被保护着没有」。先给工具栈打三态分（OK / 配了没跑 / 缺），
再按读数分诊到五条循环。

**为什么需要技能**：「配了没跑」这类静默失效不报错、只静默不成立，需要确定性脚本才能量出来；
行为层审计依赖四张契约对账表；结构简化与覆盖排序依赖图谱读数。

| 循环 | 做什么 | 依托 |
|------|--------|------|
| 补齐序列 | 白捡 → 死面 → CI → 类型 → 覆盖 → 变异，一阶段一个终态 | assurance_check.py 三态体检 |
| 覆盖循环 | 按 fan-in × 覆盖排未测代码，补能杀死变异体的断言 | coverage_targets.py |
| 行为层审计 | 四张契约对账表划范围 → 五类缺陷谱系语义审计 | manon-contract-audit.py（零模型） |
| 结构简化 | 19 条原则三层分类，A/M 面板 + C 层自动修 | 图谱健康度 + dao 系列脚本 |
| 检查退役 | 清点执行器/检查器，证明后再删，装棘轮防复发 | retire_checks.py |

**实测效果**（结构简化循环，应用于 Manon 自身代码库）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 健康评分 | 88/100 | 97/100 |
| 死代码实体 | 47 个 | 29 个 (-38%) |
| 测试覆盖率 | 32% | 61% (+29pp) |

### 技能自增强循环

基于图谱上下文写代码（query 优先于 Grep）→ /assurance 做行为层审计、补覆盖、简化结构、
退役过期门禁 → 发现的问题进入下一轮循环。

## 六、代码健康评估

Manon 从 8 个维度评估代码库的结构健康，每个维度 10 分，加权汇总为 100 分总分。

| 缩写 | 维度 | 衡量什么 | 权重 |
|------|------|---------|------|
| MC | 模块耦合度 | 跨模块依赖占总依赖的比例 | 15% |
| CD | 循环依赖 | 模块间循环依赖数量 | 10% |
| FI | 扇入集中度 | 被过多模块调用的实体比例 | 15% |
| DC | 死代码 | 零调用方的实体比例 | 10% |
| FS | 函数复杂度 | 超大函数的比例 | 10% |
| TD | 技术债务 | TODO/FIXME 注释密度 | 15% |
| MF | 模块碎片化 | 过小模块 + 过深路径比例 | 15% |
| RE | 间接层密度 | 桶式重导出的比例 | 10% |

这 8 个维度都是**图谱原生**的 —— 直接从知识图谱的结构数据中计算，不需要额外的静态分析工具。

## 七、安全与隐私

Manon 的安全设计原则是**数据不出本机**：

| 安全特性 | 机制 |
|---------|------|
| **存储全本地** | 图谱、向量、代码块全部落 `<项目>/.manon/`；无服务端、无数据库、无后台进程 |
| **源代码不出本机** | 解析由本地 tree-sitter 完成，全程无上传动作 |
| **出网调用仅两处，按键关停** | 向量嵌入（代码片段文本 → 嵌入 API，`MANON_EMBEDDING_API_KEY`，sync/query 前置）；deep-query 的 LLM 规划（检索上下文 → LLM API，`VERISPRING_API_KEY`，仅 deep-query 使用）。不配置对应 key，对应功能不可用，其余功能不受影响 |

## 快速开始

**第一步：安装（一行命令）**

```bash
git clone https://github.com/brandonzyy/manon.git
cd manon && bash install.sh --install-skills
```

安装器自动完成：Python 3.10+ 检测、venv 与依赖、`manon-kg` 包装器、技能安装到
`~/.agents/skills`。密钥经环境变量注入：

```bash
export MANON_EMBEDDING_API_KEY=sk-...   # 硅基流动（sync/query 必需）
export VERISPRING_API_KEY=sk-...        # 可选，deep-query 的 LLM 规划
```

**第二步：建图与查询**

```bash
cd <你的项目>
~/manon/manon-kg sync      # 建图/增量（落 .manon/，1-3 分钟）
~/manon/manon-kg query "认证流程在哪" -j
```

**第三步：交给 AI**

在 AI 编程会话中输入 `/manon` 载入使用规则。此后 AI 按规则工作：定位先 query 再截读、
改公共函数前先看调用方、每次任务后 sync 并入结构变化。图谱随每次 `sync` 增量前进，
`manon-kg status` 随时查看索引规模与健康度。
