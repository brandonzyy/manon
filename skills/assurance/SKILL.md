# /assurance — 工程保障体系的唯一入口

**判据只有一份**：[references/判据.md](references/判据.md)。本 skill 是它的执行流程，不重复它的定义。
**开工前先读它**（四层保证栈、两条元规则、缺陷沉降）。

## 触发
「跑一下 assurance / 体检 / 合规检查」「按体系规范补齐」「按 Day-0 清单装一下」，以及
「简化代码 / 降复杂度」「审行为层」「门禁太多 / 这些测试还有用吗」。
**不确定该走哪条，一律从这儿进**——Step 2 按读数分诊。

---

## Step 0 — 红灯裁决（见到任何失败先走一遍）

命令失败不是红灯，只是待验证结果。权威结果只有四种：`PASS`（通过）／
`RED`（基线绿＋稳定复现＋「改动→失败」因果链——**只有它能阻断或驱动改代码**）／
`INVALID`（判据、范围、基线或检查器错——修门禁，不改业务代码）／
`UNKNOWN`（环境故障、结果翻转、证据不足——停下补证据）。
每条失败留一行回执：`内容标识｜命令｜当前结果｜基线结果｜权威结果｜证据`；
同一内容、同一环境、同一命令**最多两次**，第二次无新证据即停。
七条规则、判例、重跑纪律：[references/红灯裁决.md](references/红灯裁决.md)。

## Step 1 — 体检（必做，先别动手）
```bash
python3 <SKILL_DIR>/scripts/assurance_check.py <项目路径>
```

输出三态。**三态的读法比分数重要**：

| 状态 | 含义 | 怎么办 |
|---|---|---|
| `OK` | 配置存在**且**被至少一个执行器引用 | — |
| `CONFIGURED_NOT_RUN` | 配置在，无执行器 | **最先修这一类**。它比缺更危险——看起来像装了 |
| `MISSING` | 没有 | 按 Step 4 排期 |

两条读数纪律：**CI 那格是唯一可能假绿的**——工具只看得见配置在不在，看不见平台有没有启用、
流水线跑没跑过；看到它绿要追一句「最近一次真跑绿是什么时候」。**分数不是目标**，满格但
没人看棘轮存量，等于没装。

## Step 2 — 分诊（读数决定走哪条）

**三态全绿只等于装齐了**，体系还有四条循环，各带自己的判据与工具——**打开对应 references 再动手**：

| Step 1 之后的读数 / 需求 | 走 |
|---|---|
| 有 `MISSING` / `CONFIGURED_NOT_RUN` | 留在本 skill，Step 3 起 |
| 全绿，覆盖率棘轮有零覆盖分支 / 要补测试 | [覆盖循环](references/覆盖循环.md) |
| 全绿，找测试与图谱都抓不到的行为层缺陷 | [行为层审计](references/行为层审计.md)（硬依赖 manon） |
| 降结构复杂度：耦合、重复、过度抽象、死代码 | [结构简化](references/结构简化.md)（硬依赖 manon） |
| 全绿，inventory 报重复执行／零执行／空转 | [检查退役](references/检查退役.md) |

inventory 指 `retire_checks.py inventory --root <目录>`；标了「硬依赖 manon」的两条先跑 `/manon`。

## Step 3 — 补齐（新仓走 Day-0，存量走补齐序列）

| 情况 | 走哪条 |
|---|---|
| 新仓、第一次提交之前 | `day0.py <项目>`：配置、钉版工具链、自含判据、baseline 冻结、CI 模板一次装齐（幂等；判据测试在 tests/test_day0.py）。存量为零，成本最低 |
| 存量项目 | 补齐序列，每阶段终态判据必须是**一条可跑的命令**：**一阶段一个终态，绝不并行**——同时上三个工具会一次报几千条，然后就放弃了 |

| 阶段 | 动作 | 为什么是这个顺序 |
|---|---|---|
| P1 白捡 | 找出所有 `CONFIGURED_NOT_RUN`，接上执行器 | 零边际成本，配置已经在了 |
| P2 死面 | 死代码工具 + 「每个脚本答得出谁执行它」的不变量 + 孤儿处置 | 先把仓库缩小，后面每一步都更便宜 |
| P3 执行器 | CI：PR 上从**干净克隆**跑一次 | 之后新装的检查自动获得非本机执行器 |
| P4 类型 | 类型检查 + baseline 棘轮 | 最大长期收益，但**必须 baseline** 才不至于放弃 |
| P5 覆盖 | 覆盖率测量 + 棘轮 + 零覆盖分支清单（[覆盖循环](references/覆盖循环.md)） | 依赖 CI 才有稳定基线 |
| P6 变异 | 核心模块跑一轮 | 最贵，放最后，一次性 |

执行前必做的三件事、棘轮为什么是默认形态、什么不能进提交钩子、**需要人拍板的四类**
—— 见 [references/补齐要点.md](references/补齐要点.md)。

## 硬规则

**不许只为把格子翻绿而丢一个配置文件进去**——那正是 `CONFIGURED_NOT_RUN`，本体系要防的头号失效。
每装一件工具必须同时回答「谁执行它」，并登记进那份唯一的清单。
**每件工具都要说得出它抓的是哪一类缺陷**；说不出的规则不选。报了没人修的规则会让人整个不看输出，
存量报太多时**收窄规则集**，而不是调低门槛。

## 落账

1. **跟踪线**：存量补齐建一份计划（`docs/plans/…·执行中.md` 或等价物），每个工作项带**可跑的终态判据**。
2. **事故页**：静默失效各成一页（`docs/incidents/`）；「防复发」栏除写哪个检查器守着，**还要回答
   「有没有通用工具能抓这一整类」**——有就装工具，别只写自定义检查器。
3. **回写判据**：踩到新坑就补进 [references/补齐要点.md](references/补齐要点.md)——那是给下一个执行的人的。

## 收尾

再跑一次 Step 1：**0 MISSING / 0 CONFIGURED_NOT_RUN 才算这一轮完成**，且要明确说出「CI 那格
是不是真跑绿过」，按 Step 2 说清分诊到了哪条、还是就此收工。计划里还有未闭合项时，
**状态后缀不许翻成「已完成」**——把「未开始」写成「已完成」是命名谎言。
