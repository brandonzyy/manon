# 结构简化 —— 大道至简（原独立 skill /dao，1.6.0 并入）

**理念**：Simplicity is the ultimate sophistication.
不预设问题，让知识图谱告诉我们这个项目的复杂度在哪里。原则是分类词汇，不是检查清单。

## Prerequisites（硬依赖 manon）

调 `mcp__manon__manon_repos_list`。失败 → 先跑 `/manon` 激活；仍失败 → 展示安装命令并 STOP。

```bash
pip install manon
# 加入 ~/.claude/settings.json → mcpServers → manon: { "command": "manon", "args": ["mcp"] }
```

## ⚠️ PATH RULES（调用任何脚本前先读）

本 skill 的 Python 脚本**全局安装在本 skill 目录下**，不在被分析的项目里。

```
SKILL_DIR   = 系统头里显示的 "Base directory for this skill"
              （如 ~/.claude/skills/assurance）

REPORT    = <SKILL_DIR>/scripts/dao-report.py    ← 管理 issues.json
SCANNER   = <SKILL_DIR>/scripts/dao-scan.py      ← 读图谱健康度
ANALYZER  = <SKILL_DIR>/scripts/dao-analyze.py   ← 三层程序化分析
COMMITTER = <SKILL_DIR>/scripts/dao-commit.py    ← 原子提交 + 关 issue + 图谱同步
PICKER    = <SKILL_DIR>/scripts/dao-pick.py      ← 交互式选择器
```

**项目里的 `.dao/`** = 数据目录（issues.json、quality-report.md）——不是脚本。

调用一律带全路径：
```
python <SKILL_DIR>/scripts/dao-report.py <args>
```
绝不 `python .dao/...` 或裸 `python dao-report.py`。

## 执行流程

1. `mcp__manon__manon_init(project_path)` → 提取 `repo_id`、`MANON_DIR`、`MANON_PYTHON`

2. **分析** —— 图谱驱动，不是模式驱动：
   - `python SCANNER context <project_path> <repo_id>` → JSON `{health, scan_checklist, report_exists, open_issues, changed_files}`
   - `scan_checklist` 含全部 19 条原则（A1-A7、M1-M4、C1-C8）；`priority: "high"` 表示某健康维度低于阈值——先查这些
   - `python ANALYZER <project_path> <repo_id>` → JSON `{candidates, deep_query_raw, structural}`
     - A 层：健康指标 + 图遍历（薄层、枢纽模块）
     - M 层：实体锚定的 deep_query（边界清晰度、类型重复）
     - C 层：结构分析（死代码、碎片化、深嵌套、循环依赖）
   - **首次**（`report_exists=false`）：`python REPORT init <project_path>` → 对 ANALYZER 的每个候选：`python REPORT add <project_path> <layer> <code> "<描述>"`
   - **后续**（`report_exists=true`）：加载未关 issue；重跑 ANALYZER 找**改动区域**的新候选 → 只 add 真正新的（跳过与现有未关 issue 重复的）

3. **展示面板 + 询问** —— 用 `AskUserQuestion`：
   - 只展示 **A 与 M** 的未关 issue（分组、带编号）—— C 类不逐条列
   - 有未关 C issue 时只报数量：「代码层 (C): N 个待处理，将自动批量执行」
   - 问：「选择要处理的架构/模块 issue（输入编号），或直接回车跳过进入代码层自动优化」
   - 选了 A/M → 第 4 步；跳过/回车 → 第 5 步

4. **用户选中 A/M issue**（如 `A1`、`M2`）：
   - `python REPORT arm <project_path> <issue_id> <SKILL_DIR> <repo_id>` —— 写 dao marker，hooks 才能注入提交命令
   - `EnterPlanMode` —— 计划**必须**以这个头开始（PreToolUse hook 会从它自动写 marker）：
     ```
     DAO: project=<project_path> issue=<issue_id> skill=<SKILL_DIR> repo=<repo_id>
     ```
   - 头之后只写实现内容；文档里不写后置步骤
   - 等用户批准 → `ExitPlanMode`
   - 执行实现 → 跑测试
   - `MANON_DAO_MSG="<提交信息>" python COMMITTER "<project_path>" "<issue_id>" "<SKILL_DIR>" "<repo_id>"`
   - `manon_impact(repo_id, commit='HEAD')` → 同步图谱
   - 回到第 3 步

5. **C 自动循环** —— 不停顿处理所有 C 候选：
   - 每个候选先验证：
     - C2 合并：三问闸（git 历史 · 操作类型对齐 · 命名准确）
     - 任何删除：`manon_graph` 确认零调用方
     - 不过 → 跳过，下一个
   - 实现 → `git commit` → **`manon_impact HEAD`** → **`python REPORT done <project_path> <id> <commit_hash>`** → 同步图谱——一条 issue 一个回合
   - 提交后复查：函数 ≥6 参或 >60 行 → `python REPORT add <project_path> C <code> "<描述>"`
   - 下一个候选

## 约束

1. 绝不破坏功能；测试失败即停
2. 一条原则一次提交；每次提交后同步图谱
3. 架构/模块层：单会话单 issue，Plan mode，必须人批准
4. 代码层：自动循环，无需确认
5. C2：每轮至多 1 次合并；文件变少 ≠ 更简单（结果要能一句话说清）
6. 看起来刻意的耦合或结构 → 不问就不动
