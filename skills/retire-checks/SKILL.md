# /retire-checks — 退役过期的「检查」

**退役对象**：门禁、检查器（`check_*`）、门禁执行器、测试套件、验收矩阵——所有为了「证明代码
没坏」而存在、但已不再证明任何东西的资产。不含产品代码（`/dao`）、不含补测试（`/assurance` 的覆盖循环）。

## 触发
「门禁太多了 / 测试跑太慢 / 清理一下门禁 / 这些测试还有用吗 / 被历史门禁拖累」，或直接
`/retire-checks`；也用于定期体检。不触发：补测试、简化产品代码、单条测试失败排查。

## 一、先判该不该做
**命中任意两条**才值得开工：
- 一次完整门禁里有相同检查器被执行多次，或有相位跑的是空集
- 测试语料里里程碑命名（`test_m8_*`、`test_mvp04_*`）占比过半
- 存在两个以上门禁执行器，且互相调用或彼此是子集
- 有检查器答不出「谁执行它」
- 架构在动，而每次动都要跟着改门禁

跑一次 `inventory` 就能回答全部五条。**先量，再判**——这类活最容易凭印象开工然后砍错对象。

## 二、LLM 判断 + 脚本固定动作
**LLM 只判断**：属于哪一类、退役后由谁承接、证明够不够、分几批、怎么验。**清点与算数全走 [`scripts/retire_checks.py`](scripts/retire_checks.py)**（纯 stdlib，输出 JSON）：

| 子命令 | 干什么 |
|---|---|
| `inventory` | 清点执行器/检查器/清单/测试语料，算**重复执行次数**与**零执行**项 |
| `blast-radius <路径>...` | 谁在文本里引用这些路径——「不跑全量」的唯一正当理由 |
| `vacuous` | 空转候选：选中零条测试的相、硬编码集合规模的断言、扫描不存在文件的门禁 |
| `snapshot --label X` / `diff A B` | 同一把尺量前后 |

调用：`python3 <SKILL_DIR>/scripts/retire_checks.py <子命令> [--root <项目目录>]`

🔴 **三禁**：禁凭文件名相似批量删、禁用 `--collect-only` 当验证、禁在共用工作树上做。

## 三、三分类法（核心）
| 类 | 定义 | 处置 |
|---|---|---|
| **A 决策棘轮** | 编码**已做完的决定**，设计怎么变它都不变（边界扫描、契约、归零断言、命名棘轮） | **留，且是唯一该增长的** |
| **B 行为回归** | 编码**还在动的设计**的行为细节 | 里程碑完成即退役，压成能力主路径 |
| **C 元账** | 管门禁的门禁、交付收据、验收矩阵驱动器 | 删 |

**判据不是「新旧」，是「它编码的决定还会变吗」。** 架构越动 A 类越值钱——正是它们让你敢下手
重构；B 类每动一次架构就要重写一次，那才是真成本。

健康的结果通常是：**门禁条数变多，跑得反而变快**。删掉的是重复执行和空转相，加上的是真拦得住
东西的。砍完门禁变少、覆盖也变少，多半砍错了对象。

## 四、标准流程
```bash
S=<SKILL_DIR>/scripts/retire_checks.py
python3 $S inventory --root <目录>            # 1. 量。数字原样进计划文档，每批跟它对账
python3 $S snapshot  --root <目录> --label before
python3 $S vacuous   --root <目录>            # 2. 找空转，逐条按 check 字段实际验，别信启发式
# 3. 建隔离工作树——前后对比必须排除并行会话的在途代码
# 4. 建**干净基线**：跑一次全量，失败逐条归因到环境还是代码。不归零就没有可比的「之前」
# 5. 分批。每批独立提交、独立可回滚，批与批之间对账
python3 $S snapshot --root <目录> --label after && python3 $S diff --root <目录> before after
```

## 五、删之前必须过的四道证明
一条都不能省，四道都是从实际翻车里长出来的：
1. **覆盖不丢** —— 被删对象所测的性质，指出**具体由谁承接**。对分相 pytest：证明其目标路径
   全部落在某个全量相的范围内（脚本比对，不靠眼看）。
2. **引用不悬空** —— `blast-radius` 查一遍。文档、配置、`PROJECT.yaml` 里的悬空引用一样要修。
3. **不制造空断言** —— 🔴 **被删对象若是另一条门禁的扫描目标，删了它那条门禁会静默变 PASS**
   （`grep` 找不到文件即返回非零，直接走 PASS 分支）。要么保留，要么连同那段断言一起删。
4. **不是唯一执行者** —— 删执行器前，先把它独有的能力移植走。

## 六、验证纪律
- **`--collect-only` 通过不算验证。** 实战里 646 例干净收集、import 无错，一跑起来两套测试
  互相污染、26 例炸掉。**必须真跑。**
- **先建立干净基线。** 环境缺件的假红会淹没真问题（实测：验收栈少起一个建桶容器，54 条
  `s3_put_failed` 假红）。
- **改了运行时代码就跑全量**；只改门禁脚本/配置/文档时用 `blast-radius` 算影响面跑定向验证——
  这是省时间的正当方式，不是偷懒，理由要写进提交信息。
- **同一把尺量前后**（`snapshot`/`diff` 出表），任何一行变差都要能说出理由。
- **区分 flaky 与回归**：单跑三次、看改动是否在失败路径上、看是否碰过运行时代码。墙钟断言
  （`p95 <= 2.0`）和与后台常驻循环抢状态的计数断言，都是「随机失败但什么也没保护」的典型——
  同一用例里通常已有机器无关的真不变量，删掉错的仪器、留下那条即可。

## 七、装棘轮（不装就会长回来）
删完必须落三条机械约束，否则半年后回到原点：
1. **测试按能力命名，不按里程碑命名。** 里程碑会完成，能力不会。存量登记成清单、**只许变短**，
   增删都要同提交登记（照迁移 hash 冻结的成法）。
2. **`check_*` 即门禁，门禁即清单。** 每条都要答得出「谁执行它」，合法答案只有 `invoked-by:` /
   `phase:` / `manual:` 三种标签且必须指向真实存在的东西。🔴 **「由某测试覆盖」不是合法答案**
   ——测试测的是检查器的逻辑，不等于有人执行它。没人执行的检查器是纯开销，它的测试是开销的平方。
3. **新建里程碑门禁必须写死期**：何时退役、退役后由哪条能力测试承接。写不出死期的门禁不批。

参考实现见 [references/ratchets.md](references/ratchets.md)，实战踩坑见 [references/traps.md](references/traps.md)。

## 八、报告口径
收口报告要有：前后度量表（同一把尺）、每批的提交 sha、**没做完的部分和为什么**。尤其最后一条
——「行为测试的逐文件去重」通常做不完，说清它需要逐条比对断言、按文件名相似批量删正是这套方法
反对的做法，比假装完成有用得多。
