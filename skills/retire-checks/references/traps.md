# 实战踩坑（一次门禁与测试精简专项，5 个提交）

每条都真实发生过，不是设想。

## 一、手工盘点一定会漏
用 `ls scripts/run_*gate*` 盘点执行器，漏掉了 `scripts/release-gate/run_release_gate.sh`
——它在嵌套目录里。真实基线是 **8 个执行器不是 7 个**，报给用户的数字错了一轮。

`inventory` 递归走全树，且对「什么算执行器」用信号判定（跑 pytest / 点名检查器 /
有相位 / 读清单）而不是文件名 glob。**清点交给脚本。**

## 二、`--collect-only` 通过不算验证
两套测试目录各有一个同名 `support` 包，各自 `sys.path.insert` 到自己目录。删掉同名的
`test_gate_driver.py` 之后，646 例 **collect-only 干净收集、零报错**——看起来可以合并成
一次 pytest 调用了。

一跑起来：先到者赢，第二套的 26 例全部拿到第一套的 `support`，**26 failed + 26 errors**。

改名成 `support_m8` / `support_m809` 之后再跑，还剩 4 个失败。继续单跑对照：
`tests/m8` 单跑 **40/40 全绿**，两套同跑就挂 3 条权限否定断言——**跨套件全局状态干扰**。
最终结论是分三次 pytest 调用，不是一次。

> 「删完跑一遍 collect-only 就算验证」不成立。**必须真跑，而且要单跑对照。**

## 三、删掉扫描目标 = 把那条门禁变成空断言
`check_acceptance_readiness.sh` 的豁免登记写着「现仅历史文档引用」，看起来可删。
但 `check_channel_zero_boundaries.sh` 靠 `rg <飞书/钉钉凭据模式> <该文件>` 来断言
「核心就绪不得要求可选企业渠道凭据」。

删掉被扫描的文件，`rg` 找不到即返回非零，那条断言**直接走 PASS 分支**——一条真边界
门禁静默变成永远通过。

> 删任何东西之前，查一遍谁把它当**扫描对象**。要么保留，要么连那段断言一起删。

## 四、「由某测试覆盖」不等于有人执行它
三条豁免登记写着「由 `tests/m0/test_check_xxx.py` 覆盖」。那个测试测的是**检查器的
逻辑**，而检查器本身没有任何执行者。其中 `check_m6_real_acceptance.py` 有 568 行、
是仓里最大的检查器，**退出码恒为 2**（它在等真实手机/微信验收），永远不可能在任何
清单里通过。

它不是门禁，是状态报告器。处置是改名 `report_*` 移出 `check_*` 命名空间。

> 一个没人执行的检查器是纯开销，它的测试是开销的平方。

## 五、靠「什么都不测」来通过的门禁
`run_mvp04_gate.sh` 的 `performance` 相跑
`pytest test_mvp04_pilot.py -k 'latency or performance'`——而那个文件里**没有任何**
匹配的用例。它选中零条测试，然后打印 `PASS performance`。

`vacuous` 子命令专门找这类：分相选择器（拿去 `--collect-only` 数一下）、硬编码集合
规模的断言、扫描不存在文件的门禁。

同类还有 `check_mvp04_acceptance_structure.py` 里的
`if len(migrations) != 88 or migrations[-1].stem != "092_xxx"`——每加一条迁移就必须回来
改门禁（这是它成为改动次数最高检查器的唯一原因），而改错内容、编号重复、缺失回滚
它一概拦不住。换成真不变量：编号三位、唯一、命名规范。

## 六、环境缺件产生整片假红
隔离树只起了 postgres + minio 就跑全量，**54 条失败**，全是 `s3_put_failed`——少起了
建桶的 `minio-init` 容器。补桶重跑，那批 100% 绿。

> 基线不归零就没有可对比的「之前」。先把失败逐条归因到环境还是代码。

## 七、分清 flaky 与回归
批 0 之后全量多出 1 条失败，看起来像回归。三条证据判定为既有 flaky：

1. 隔离下连跑 3/3 通过
2. 本批在 `services/api/caseos_api/` 下**零改动**，不可能影响运行时
3. 基线里它能过，恰恰是因为当时环境更差（54 条挂着、DB 活动少、竞态窗口没撞上）

真因：`assert counts["sessions"] >= 1` 与 `main.py` 里常驻的 `run_hygiene_loop` 抢同一条
陈旧会话——后台先删了，显式调用就数到 0。

另一条 `assert p95 <= 2.0` 是**墙钟**断言，机器一忙必翻转。

> 两条都是「随机失败但什么也没保护」。它们想守的性质通常在同一个用例里已有机器无关
> 的断言（`scanned <= 400`、「陈旧的没了新鲜的还在」）。**删掉错的仪器，留下那条。**

## 八、统计必须排除 node_modules
第一次统计测试语料，`tests/e2e` 报 67,344 行、`tests/node-integration` 报 124,099 行。
点进去一看：TypeScript 编译器的打包源码（`typescript.js` 一个文件 196,073 行）。

真实测试代码是 4,382 行和 1,177 行。**虚报了 19 万行。**

## 九、并行会话会污染归因，也会抢资源
施工全程有 3–4 个并行会话在同一台机器上跑各自的全量。18 核负载 11.9 时，一次全量从
13 分钟涨到 40+ 分钟，还会让墙钟断言和大数据量夹具（插 10 万行）直接超时。

对策：在隔离工作树里做（`git worktree add`，并把 venv / 容器 project 名 / 端口一起隔离）；改动只碰门禁脚本/配置/文档时，用
`blast-radius` 算影响面跑定向验证，并把理由写进提交信息。

## 十、影响面匹配不能用裸文件名
第一版 `blast-radius` 拿 `Path(t).name` 当匹配键，于是 `scripts/README.md` 用
`README.md` 去全仓匹配，把一个毫不相干的 Node 测试算进了影响面。

现在只在**文件名全仓唯一**时才用作匹配键。影响面宁可窄一点也不能虚——虚的影响面
会让人以为验证过了。

反过来也发生过：手工 grep `README.md` 让我以为 `test_project_collaboration.py` 读
`scripts/README.md`，实际它是在临时 git 仓里自己造了个 `README.md`。**工具比手工准。**
